# Phase 18.6 handover: FastAPI end-to-end integration and retrieval validation

Phase 18.5 provides one explicit experimental Ollama Native Gateway runtime for frozen Q1S and R3. The [architecture report](architecture_and_integration.md) contains settings, exact schema evidence, identity TTL, ownership, error behavior and operational limitations; the [test report](integration_test_report.md) separates offline, live inference and mocked retrieval evidence. Production routes remain disabled/pending. Phase 18 remains `IMPLEMENTED_PENDING_BACKUP_VALIDATION`; T17 is untouched and exhausted.

1. Verify actual PostgreSQL connectivity and required schema/index/catalog state without exposing the DSN. Start the existing FastAPI lifespan with current local TF-IDF/BGE assets and explicit native experimental settings. Refresh time-limited route/model evidence rather than reusing expired smoke approvals. Record model tag/digest, source/config/schema hashes and runtime settings. Use one worker while quota is process-local.
2. Exercise actual pgvector dense retrieval, TF-IDF and hybrid contracts. Preserve original queries, QU extracted/transformed constraints, retrieval candidates and reranker results. Measure database/network, preference encoding, retrieval, reranking, each inference stage and whole HTTP request latency separately under the existing 90-second API/95-second bot budgets. Distinguish cold model startup from warm requests.
3. Validate RRF and relevant existing reranking methods without redesigning retrieval or reopening prompts. Evaluate product type, price/rating/brand constraints, compatibility requirements and mandatory features against authoritative catalog evidence. Obtain route evidence for actual dynamic schema shapes before admitting them; a family marker alone is insufficient.
4. Preserve and reproduce these negative retrieval cases: **wireless charging pad → Lightning cable; Bluetooth speaker → headphones; Honda City body cover → steering cover**. R3 must continue refusing them. Do not relax R3 relevance or mandatory-feature guards to make retrieval look successful. Track legitimate synonyms and coverage separately.
5. Reproduce the downstream exclusion-guard mismatch for valid numeric expressions (for example `not exceeding`/other recognized price negation). Frozen Q1S protects parsed numeric spans, while older API/recommendation/preference exclusion checks can still reject valid expressions. Record the exact failing layer and apply a narrowly justified downstream compatibility correction with positive numeric and genuine-exclusion negatives. Do not remove exclusion safety globally or silently rewrite bounds.
6. Validate actual `POST /api/v1/recommend` request/response and alias, clarification/invalid/unsupported/no-results statuses, authoritative URLs/images assembled by the API, language behavior, token/model/latency metadata, fallback attribution and telemetry correlation. Keep public contracts unchanged and count outbound inference: maximum one QU plus one R3, with no repair/judge/cloud backup. Exercise actual eligible candidate counts and ensure unsupported schema shapes fail safely.
7. Test failure propagation at API boundaries: Ollama unavailable, stale/mismatched identity, quota contention, malformed/truncated provider output, retrieval/DB failure, expired parent budget and client cancellation. A parent deadline/cancellation must not be mislabeled as successful fallback. Readiness must separate DB/assets, route configuration, recent identity and provider cooldown. Decide an explicit identity re-verification policy for longer sessions; the current 300-second cache fails closed until re-verification or restart.
8. Only after API validation, run the existing Telegram client against that API and verify actual user delivery, authoritative catalog links/cards, session behavior and safe error/fallback messages. Telegram remains presentation-only. Do not introduce direct LLM/DB access in the bot or a public Ollama tunnel.

Independent semantic/usefulness/language review remains open. Q1S's historical preference F1 is 68.4%, answerable coverage 11/16; source quotation assembly avoids free factual generation but does not prove suitability or catalog truth. Validate coverage and quotation usefulness independently, without additional inference passes in the runtime.

The local-only native profile intentionally has no cloud backup. It does not close the historical approved-backup/failover gate. Resolve that production scope explicitly through a separate recorded decision; never mark Phase 18 complete from native adapter or schema success alone. No production approval, public deployment, new model, fine-tuning, historical ledger reset, commit or push is implied by this handover.
