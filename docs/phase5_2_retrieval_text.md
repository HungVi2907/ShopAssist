# Phase 5.2 — Retrieval Text Construction & Validation

## 1. Objective

Phase 5.2 focuses on constructing, validating, and auditing the canonical `retrieval_text` field for all **8,405 cleaned products** produced at the end of Phase 4.

The `retrieval_text` field serves as the unified semantic textual representation for each product across the multi-stage retrieval architecture of **ShopAssist**:
1. **Sparse Lexical Retrieval (TF-IDF Baseline):** Keyword-based inverted indexing and term matching.
2. **Dense Vector Search (`pgvector`):** 384-dimensional dense semantic embeddings generated by `BAAI/bge-small-en-v1.5`.
3. **Cross-Encoder Reranking:** Query-document cross-attention scoring for fine-grained ranking.
4. **LLM Context Synthesis:** Grounded context feeding query understanding and product comparison generation.

No embedding vectors are generated in this phase; the scope is strictly limited to deterministic text construction, quality validation, edge-case audit, and intermediate dataset artifact persistence.

## 3. Retrieval Text Design

The `retrieval_text` string follows a structured, template-driven format delimited by `" | "`:

```text
Product: <product_name> | Category: <category> | Brand: <brand> | Specifications: <specs> | Description: <description>
```

### Key Principles:
1. **Anchor Entity Context:** The product identity and taxonomy are established first.
2. **Dynamic Segment Omission:** Optional fields (`Brand`, `Specifications`, `Description`) are completely omitted when missing, empty, or composed solely of invalid placeholder data. No empty segments or dangling delimiters are produced.
3. **No Garbage Tokens:** Never emits corrupt placeholder tokens such as `Brand: None`, `Brand: nan`, `Brand: null`, or `Description: None`.

---

## 4. Field Ordering

The field ordering is strictly fixed and mandatory:

```text
1. Product: <product_name>
2. Category: <category>
3. Brand: <brand>
4. Specifications: <specs>
5. Description: <description>
```

### Architectural Rationale:
- **`Product` and `Category` (Anchor Fields):** Placed at the very beginning to establish the primary entity identity and domain context for both dense transformer self-attention and sparse TF-IDF term frequencies.
- **`Brand` (Contextual Identity):** Follows category to provide high-signal entity context.
- **`Specifications` (High Information Density):** Contains dense, factual, distinguishing technical attributes (e.g., `Material`, `Connectivity`, `Dimensions`, `Compatibility`). Placing specifications *before* description ensures this critical information is never clipped.
- **`Description` (Tail Content):** Descriptions contain redundant marketing language and varying lengths (up to 4,433 characters in the raw data). Placing description at the very end guarantees that safe truncation never discards structured metadata or technical specifications.

---

## 5. Specification Formatting

The `product_specifications` column contains JSON arrays of key-value dictionaries:
```json
[
  {"key": "Occasion", "value": "Casual"},
  {"key": "Sole Material", "value": "PVC"}
]
```

### Flattening Rules:
- Flattened into a semicolon-separated string: `Key1: Value1; Key2: Value2; Key3: Value3`.
- Internal whitespace within keys and values is normalized.
- Keys or values that are empty, null, or match invalid placeholders (`na`, `n/a`, `none`, `null`, `nan`, `nil`, `undefined`) are eliminated.
- Handled safely via `json.loads` without using Python's `eval()`.
- Robust against malformed inputs (non-dict items, non-list containers).
- If all items in a product's specifications are invalid or empty, the entire `Specifications:` segment is omitted.

## 6. Null / Missing Value Handling

Missing attributes are handled by conditional segment emission rather than emitting placeholder text:

| Scenario | Raw Value | Emitted Segment | Example Output |
| :--- | :--- | :--- | :--- |
| **Full Data** | All fields present | All 5 segments emitted | `Product: ... \| Category: ... \| Brand: ... \| Specifications: ... \| Description: ...` |
| **Missing Brand** | `None`, `""`, `"nan"` | `Brand` segment omitted | `Product: ... \| Category: ... \| Specifications: ... \| Description: ...` |
| **Empty Specs** | `[]`, `"{}"`, `None` | `Specifications` segment omitted | `Product: ... \| Category: ... \| Brand: ... \| Description: ...` |
| **Missing Description** | `None`, `""`, `"null"` | `Description` segment omitted | `Product: ... \| Category: ... \| Brand: ... \| Specifications: ...` |
| **Missing Brand & Specs**| Both absent | Both segments omitted | `Product: ... \| Category: ... \| Description: ...` |

## 7. Description Truncation Strategy

The planned embedding model (`BAAI/bge-small-en-v1.5`) operates with a context window of **512 tokens** (~1,800 – 2,000 characters). 

### Truncation Policy:
- Default threshold: `max_chars = 1200` characters.
- If description length $\le 1200$: preserved completely after whitespace normalization.
- If description length $> 1200$:
  - If the character immediately following position 1200 is whitespace, the string is cleanly cut at index 1200: `text[:1200].rstrip()`.
  - Otherwise, the nearest preceding space within `[:1200]` is located (`last_space = candidate.rfind(" ")`).
  - The description is cut at `last_space`: `candidate[:last_space].rstrip()`.
  - In the rare edge case where no space exists within 1200 characters (single unbroken token), the string is sliced at 1200.
- **Word Boundary Guarantee:** Words are never split in half (e.g., `Bluetooth` is never truncated into `Blue`).
- Trailing whitespace is stripped cleanly.

---

## 8. Why Price and Rating Are Excluded

Numerical hard constraints (`discounted_price`, `retail_price`, `rating`) are **strictly excluded** from `retrieval_text`:

1. **Transformer Attention & Numerical Reasoning:** Dense vector embeddings generated by BERT-style models cannot perform numerical range comparisons. A vector for price `749` is not semantically adjacent to `750` in a continuous mathematical sense.
2. **Guaranteed 100% Deterministic SQL Filtering:** Budget constraints and customer rating thresholds are enforced via SQL expressions on indexed relational columns (`WHERE discounted_price <= :max_budget AND rating >= :min_rating`).
3. **Noise Reduction:** Injecting prices into semantic embeddings causes false positive matches (e.g., user asks for "1080p monitor" and matches a monitor priced at 1,080 rupees). Excluding numbers preserves semantic fidelity.

## 10. Validation Rules

Every constructed `retrieval_text` must satisfy:
1. **Non-null & Non-empty:** Cannot be `None`, empty string, or whitespace-only.
2. **Required Prefixes:** Must begin with `Product: ` and contain ` | Category: `.
3. **Absence of Corrupted Placeholders:** Forbidden regex check ensuring strings like `Brand: None`, `Brand: nan`, `Description: null` never occur, while valid brand names (e.g., `Nanson`) are preserved.
4. **Dataset Integrity:** Input row count (8,405) must equal output row count (8,405). `product_id` alignment must match 1:1.

## 15. Issues / Limitations

1. **Extreme Specification Outliers:** A few products (under 1% of the catalog) have extraordinarily exhaustive specifications (up to 32 pairs, ~2,600 characters). Because specifications are prioritized over descriptions and descriptions are capped at 1,200 characters, these rare items reach ~3,500 – 3,975 characters (~800 – 950 tokens). The embedding model tokenizer will naturally truncate tokens beyond 512, but because the most critical specifications and all anchor fields appear first, semantic representation remains high quality.
2. **Residual Marketing Boilerplate in Raw Descriptions:** Some Flipkart descriptions contain boilerplate promotional text (e.g., "Only Genuine Products. 30 Day Replacement Guarantee."). Because this occurs at the end of descriptions, it does not impede the primary semantic tokens located in product names, categories, brands, and specifications.
