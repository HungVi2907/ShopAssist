# Phase 5.1 — Product Knowledge Base Data Model & Schema Specification

## 1. Architecture Overview

ShopAssist is an end-to-end conversational product recommendation system that integrates LLM-based query understanding, structured deterministic filtering, and semantic hybrid retrieval. 

The **Product Knowledge Base** serves as the unified persistence and retrieval foundation for all catalog items. It enables:
- **Exact Structured Filtering:** Deterministic elimination of candidate products that violate hard user constraints (category, budget, brand) via relational SQL queries.
- **Dense Vector Search:** Sub-30ms semantic similarity matching over unstructured product features using dense embeddings in `pgvector`.
- **Grounded LLM Prompting:** Structured metadata and technical specifications feeding the generation layer to produce transparent, hallucination-free product recommendations with trade-off explanations.

## 2. Production Database Choice

### Decision: Supabase Cloud Managed PostgreSQL + pgvector
The production environment of ShopAssist officially uses **Supabase Cloud managed PostgreSQL with the `pgvector` extension**.

### Rationale:
1. **Managed Cloud Infrastructure:** Supabase provides fully managed PostgreSQL 15+, automated backups, connection pooling via Supavisor, and native pgvector support without manual server administration.
2. **Low-Latency Hybrid Queries:** Running relational SQL filtering and vector search in the same database engine prevents data synchronization lag and eliminates network latency between separate vector and SQL stores.
3. **Local Development Parity:** Developers can run local PostgreSQL with the `pgvector` extension (via Docker Compose `ankane/pgvector`) for offline development and CI integration, ensuring 100% dialect compatibility.

## 3. `products` Table Architecture

ShopAssist V1 adopts a **Single-Table Architecture (`products`)**.

### Why Not Split Tables?
- **Scale:** The cleaned catalog contains exactly **8,405 products**. The total table footprint (including 384-dimensional vectors and JSONB specifications) is ~25 MB.
- **Filtered Vector Search Performance:** The primary retrieval query in ShopAssist filters candidates by category and budget before sorting by vector cosine distance:
  ```sql
  SELECT product_id, product_name, brand, discounted_price, image,
         1 - (embedding <=> :query_vec) AS similarity
  FROM products
  WHERE category = :cat AND discounted_price <= :max_price
  ORDER BY embedding <=> :query_vec
  LIMIT 20;
  ```
  In a single table, PostgreSQL plans this in a single index scan without foreign key `JOIN` overhead.
- **Avoids Premature Optimization:** Partitioning into `products_metadata` and `products_embeddings` adds foreign keys and multi-table migration overhead with zero performance benefit at an 8.4K catalog scale.

## 6. Integrity Constraints

```sql
-- Non-empty strings
CHECK (length(trim(product_name)) > 0)
CHECK (length(trim(category)) > 0)
CHECK (length(trim(retrieval_text)) > 0)

-- Strict positive operational price
CHECK (discounted_price > 0)

-- Non-negative reference retail price
CHECK (retail_price IS NULL OR retail_price > 0)

-- Bounded rating score
CHECK (rating IS NULL OR (rating >= 1.0 AND rating <= 5.0))

-- JSONB default
DEFAULT '[]'::jsonb
```

## 7. `product_specifications`: JSONB Decision

### Why `JSONB` as Source of Truth?
1. **Preserves Structured Key-Value Pairs:** The Phase 4 cleaned dataset transformed raw Ruby hashes into a standard JSON list of pairs `[{"key": "Color", "value": "Black"}, {"key": "Material", "value": "Leather"}]`. Storing this as `JSONB` guarantees type safety and prevents formatting loss.
2. **No Redundant `specifications_text` Column:** Because `retrieval_text` already contains the flattened, search-ready representation (`Specifications: Color: Black; Material: Leather`), adding another column `specifications_text` would create redundant storage and require dual-field synchronization.
3. **Dynamic Presentation Layer:** FastAPI can query `product_specifications` directly and format it dynamically for whatever downstream consumer needs it (Markdown bullets for LLM prompt context, or compact key-values for Telegram Bot cards).
4. **Supabase PostgREST Support:** PostgREST automatically exposes JSONB columns as native JSON in HTTP responses.

## 8. `retrieval_text` Role and Specifications

`retrieval_text` is the canonical textual synthesis of each product used for:
- Baseline 1: TF-IDF sparse lexical search (Phase 6).
- Baseline 2 & Proposed: Dense vector embedding generation (Phase 5.3, 5.5, 7).
- Cross-Encoder Reranker input context (Phase 11).

### Formatting Template:
```text
Product: <product_name> | Category: <category> | Brand: <brand> | Specifications: <specs> | Description: <description>
```

### Critical Rules:
1. **No Prices or Ratings:** Hard numerical inequalities (`price <= 800`) are handled by SQL. Adding numerical prices to `retrieval_text` dilutes semantic attention and causes keyword false positives.
2. **Omit Missing Fields Completely:** If `brand` is null, omit the `| Brand: ...` segment. Never output string placeholders like `"Brand: None"`.
3. **Truncate Description at ~1,200 Characters:** Ensures `retrieval_text` stays comfortably under the 512-token context window of `BAAI/bge-small-en-v1.5`.

## 9. Embedding Field Specification

- **Model:** `BAAI/bge-small-en-v1.5`
- **Vector Dimension:** `384`
- **SQL Column Type:** `vector(384) NOT NULL`
- **Distance Metric:** Cosine Similarity (`vector_cosine_ops`, operator `<=>`)
- **Cosine Score Calculation:** $\text{similarity} = 1 - (\text{embedding} \Leftrightarrow \text{query\_embedding})$

### Why BGE-Small (384-d)?
- **Retrieval Performance:** Achieves **51.7 NDCG@10** on MTEB retrieval benchmarks (vs 41.9 for `all-MiniLM-L6-v2`).
- **512 Token Context:** Accommodates full product specifications and descriptions without premature truncation.
- **Resource Footprint:** 384 dimensions require half the RAM and index storage of 768-d models, keeping HNSW index memory under 20 MB on Supabase Cloud.

## 10. Versioning & Operational Fields

1. **`embedding_model VARCHAR(64) NOT NULL DEFAULT 'BAAI/bge-small-en-v1.5'`**:
   - Records which model generated the vector in each row. Enables multi-model experimentation and automated re-indexing detection.
2. **`created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`**:
   - Tracks data ingestion history.
3. **`updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`**:
   - Automatically updated on record changes via the `update_products_updated_at` PostgreSQL trigger.

## 11. Index Strategy

```sql
-- Relational B-Tree Indexes
CREATE INDEX idx_products_category ON products (category);
CREATE INDEX idx_products_price ON products (discounted_price);
CREATE INDEX idx_products_brand ON products (brand);

-- Composite B-Tree Index for primary hybrid query pattern
CREATE INDEX idx_products_category_price ON products (category, discounted_price);

-- HNSW Vector Index for Cosine Similarity
CREATE INDEX idx_products_embedding ON products
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

### Why HNSW over IVFFlat?
- **No Training Step:** HNSW builds the graph incrementally upon insert.
- **High Recall Under Filtered Search:** HNSW maintains >98% recall when combined with SQL `WHERE` clauses. IVFFlat suffers severe recall drop under filtered queries.
- **Index Memory:** At 8,405 rows $\times$ 384 dimensions, the HNSW graph requires ~18 MB of RAM, well within Supabase's memory bounds.

## 12. Lineage Fields

- **`product_id`**: Serves as the primary key and maps 1:1 to raw `uniq_id`.
- **`pid`**: Retained in production table (`VARCHAR(64) NULL`) for catalog debugging and trace audit.
- **`image`**: Retained in production table (`TEXT NULL`) for visual card rendering in Telegram.
- **`uniq_id`**, **`crawl_timestamp`**, **`is_FK_Advantage_product`**: Archived in `data/interim/cleaned_candidates.parquet` and `data/raw/flipkart_products.csv`. Omitted from production table to avoid redundant storage.

## 14. Deferred Indexes and Future Optimizations

The following indexes are intentionally deferred:
- **`idx_products_rating` (B-Tree on `rating`):** In V1, rating is only an optional reranking multiplier, not a primary search filter. An index is unnecessary.
- **`idx_products_specs_gin` (GIN on `product_specifications`):** V1 handles specification matching via semantic vector search. GIN indexing will only be added if direct SQL JSON key queries are introduced in V2.
- **`idx_products_fts` (Full-Text Search on `retrieval_text`):** The TF-IDF baseline runs in Python/scikit-learn for experimental benchmarking. Database FTS is unnecessary in V1.
- **IVFFlat:** Deprecated in favor of HNSW for small-to-medium high-recall catalogs.
