# Phase 18.1 — local query understanding audit and evaluation

Date: 2026-11-26 (Asia/Saigon). Status: **experimental; not production ready**. Phase 18 remains `IMPLEMENTED_PENDING_BACKUP_VALIDATION`. This investigation did not change production code, routes, schemas, taxonomy, or the T17 ledger.

## Executive decision

Native Ollama returned parseable, schema-conforming JSON for all 120 primary development requests and all 20 held-out requests. Nevertheless, P4, frozen on development data, inverted price direction on 9/20 held-out cases and hallucinated a brand, price, or rating constraint on 10/20. These counts are case-level, can overlap, and are measured against the supplied labels. Existing experimental rules left all nine inversions. These critical errors rule out production activation of this configuration. P4 is the most promising *test candidate* under the predeclared priority of fewer price inversions, not an accepted implementation. Its 3/20 shared-slot exact matches exclude semantic-query wording, clarification-reason wording, and v2-only fields. Neither syntactic validity nor speed establishes safety.

Best next step is **Option D: evaluate a larger local model offline**, after operator authorization for any download. Retain the current production contract and compare it with the same fixtures and prompts. A separately reviewed, tightly scoped deterministic price guard may be studied, but existing rules demonstrably do not repair these inversions, and no production change is recommended from this pilot. Any new provider integration or activation needs the existing Phase 18 route-specific acceptance and approval process; T17 remains open.

## Source-backed architecture and contract

1. `src/shopassist/llm/query_understanding.py:81` rejects non-string, empty, and over-500-character queries. `:143` applies `build_user_prompt` (`src/shopassist/llm/prompts.py:76`), wrapping the trimmed query in quoted text. The active default system instruction is `SYSTEM_INSTRUCTION` (`prompts.py:11`). Input remains untrusted; quoting alone is not an injection boundary.
2. The engine calls either legacy `GeminiClient.generate_structured_async` (`query_understanding.py:181`, `gemini_client.py:112,218`) or a Gateway request (`query_understanding.py:146-158`, `llm_gateway/gateway.py:232-237`). Gateway identifies `phase8.query.v1` (`llm_gateway/schema_ids.py:5`) and validates the decoded result as the caller's schema. The native Ollama runner here mirrors system/user construction and schema but is **not** an end-to-end Gateway or Gemini execution.
3. The provider response is JSON-parsed and validated against Pydantic v2 `QueryUnderstandingOutput` (`schemas.py:102`; `HardConstraints` at `:15`). Only `semantic_query` is required in the generated JSON Schema. Pydantic fills omitted fields, coerces some values, normalizes currency, strips/deduplicates preferences, and rejects negative price, out-of-range rating or reversed two-sided ranges (`schemas.py:15-159`). JSON Schema compliance alone cannot prove extraction completeness or semantic correctness.
4. Production calls `validate_and_normalize_output` (`query_understanding.py:190`; `normalization.py:305`), which normalizes category/brand/currency and flags foreign currency or noncanonical non-null category. A null category by itself is not enough to identify unsupported products. Pydantic can reject an invalid two-sided range before the normalization range check executes. Production returns `QueryUnderstandingResult` or a fail-closed failure path. It does **not** call `apply_rule_based_refinement_v1` (`refinement_rules.py:243`); that function is an experimental comparison only.
5. `FEW_SHOT_EXAMPLES` (`prompts.py:60`) is a standalone list of query/explanation pairs, not complete JSON demonstrations, and is never added by the production builder or engine. `prompt_variants.py` and `schema_variants.py` define experimental E1/E5, refined v2 and RequiredV2 (`schema_variants.py:151,281`); `experiments/runner.py` selects them for experiments. They are not the frozen production selection. The experimental v2 adds product type, inclusivity and exclusions; v1 cannot represent the latter two. The Phase 8 contract describes v1 price filtering as inclusive (`docs/phase8_query_contract.md:177`); a strict “under” is represented by its boundary value with no strictness bit. Do not subtract a cent or introduce a taxonomy/schema change without a separate contract decision.
6. `security.py:1` is diagnostic redaction, not a semantic prompt-injection filter. Phase 8 freeze and Phase 8.2 documents record unresolved preference, negation, label-quality and security issues, and defer larger live prompt/schema/temperature comparisons (`docs/phase8_freeze_and_handover.md:32-44`; `docs/phase8_2/final_engineering_report.md`).

## Method and reproducibility

The pilot `data/interim/phase18_1/dev_pilot.json` has 24 cases: 14 Phase 8.1 development fixtures and 10 separately constructed cases including the reported query, corrections, ambiguity, unsupported category, foreign currency, two injection attempts and one Vietnamese query. QU007 was excluded because its T-shirt label is Footwear, inconsistent with the canonical mapping. Historical fixtures contain subjective and sometimes disputed preferences; labels were not independently adjudicated. `tests/fixtures/heldout_evaluation_cases.json` (20 cases) was first evaluated only after P4 was frozen in `candidate_freeze.md`. Held-out cases include exclusion/strictness expectations that v1 cannot represent; those fields are explicitly outside the shared-slot score, and this materially limits a claim of full intent accuracy.

The runner uses HTTPX directly against `http://localhost:11434/api/chat`, `stream=false`, the production `QueryUnderstandingOutput.model_json_schema()`, production prompt construction and input validation, and the real catalog brand set. Each fresh output directory stores prompt and schema snapshots and SHA-256 hashes, model digest, dataset hash, options, every request result, raw envelope and text, parsed values, Pydantic result, normalized result, optional experimental refinement, warnings, error, token counts and timing. `jsonschema` is required for the standalone strict JSON Schema audit and was already present locally; no dependency was added. Pydantic success and JSON Schema success are tracked separately. `summary.json` is reproducible from JSONL; results can depend on server version, hardware, model and catalog data.

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_ollama_query_understanding.py --dataset data/interim/phase18_1/dev_pilot.json --variants P0 P1 P2 P3 --out data/interim/phase18_1/my_new_run
.\.venv\Scripts\python.exe scripts/summarize_ollama_query_understanding.py data/interim/phase18_1/my_new_run
.\.venv\Scripts\python.exe -m pytest tests/test_ollama_query_understanding.py -q
```

Output directories must not exist, so historical runs are never overwritten. Experimental `--schema-mode required` changes only the separate probe's schema; it was not used in the main comparison. Run sequence and timestamps are in each manifest. The held-out run used exactly the frozen P4 prompt hash and production schema. P0 is unmodified production; P1 compact; P2 field-organized; P3 P2 plus four complete constructed examples; P4 P2 plus two high-value examples, chosen after P0–P3 review. The runner's frozen file and manifest are authoritative.

Scoring: per-field exact match is case-insensitive for strings; every attempted case is in the denominator, including failures. Preference precision/recall/F1 are micro-aggregated over exact case-folded preference strings. Shared-slot exact requires all six hard fields, clarification flag and exact preference set; it excludes free-form semantic and reason text and v2-only fields. Inversion counts a predicted lower bound for a sole expected upper bound or vice versa, even if the correct bound also appears. Hallucination counts a non-null brand, min/max price or rating where its labeled counterpart is null; missing counts an expected category, brand, min/max price or rating that is null/missing. These are diagnostic counts, not causal attribution, and category errors count as missing only when null. Missing-field rate checks the complete desired v1 slots even though most are not required by the production JSON Schema. Latency P95 uses nearest rank; warm mean excludes first request of each variant, not an independently controlled restart.

## Controlled hypotheses

| Hypothesis | Classification | Evidence and limit |
|---|---|---|
| H1: insufficient instruction-following capacity | Partially supported | Numerous basic constraints fail even with examples and valid JSON, but no larger-model controlled comparison exists; cannot establish a model-size threshold. |
| H2: excessive production prompt complexity | Inconclusive | P1/P2 are shorter but degrade completeness; P2→P3 adds examples and improves category. Prompt length, examples and field ordering do not independently establish complexity as root cause. |
| H3: custom model conflict | Inconclusive | Same weights/template/system as base, no explicit custom stop; base P0 probe also failed. 2/6 raw outputs exactly matched custom and settings may differ in inherited sampling. No evidence of a conflicting custom instruction, but causation is not excluded. |
| H4: schema descriptions/optional fields | Partially supported | P0/P1/P2 legally omit slots and Pydantic defaults them. Requiring every field on six probe cases removed omissions but P0 still had 3/6 inversions and 0/6 category; this separately changes schema only. Descriptions themselves were not isolated. |
| H5: examples ineffective/not sent | Supported for not sent; efficacy partially supported | Production list is not in request. P2→P3 same instructions plus four examples increased category from 4/24 to 21/24 and completeness, but still 8/24 inversions; other prompt comparisons cannot isolate examples. |
| H6: confuses constraints/preferences | Supported | Raw outputs contain inverted bounds, invented cheap preferences and budget text in preferences/semantic query; P4 SQL-adversarial case places 30000 in minimum instead of maximum. No claim about internal mechanism. |
| H7: truncation/configuration | Inconclusive | Input token counts and termination reasons do not indicate truncation; they do not prove effective full attention. Base/custom outputs differ in 4/6 on a small probe with inherited defaults, so settings/identity cannot be ruled out. |
| H8: postprocessing | Supported as failure to correct, not proven introduction of inversion | P4 raw and normalized both have 6/24 dev inversions and 9/20 held-out; experimental rules also leave them. Validation fills omitted defaults and normalization changes categories, brands and clarification. |

Three repeated P4 runs on six development cases produced identical parsed JSON within each case (18 calls); this is limited stability evidence, not a determinism guarantee. Two adversarial inputs requested prompt disclosure or SQL: P4 did not emit those strings as generated code or system disclosure in the observed JSON, but omitted the explicit upper budget in one and inverted it in the other. Two examples cannot establish resistance to other attacks. Unsupported pet-food query failed clarification under P0/P3/P4; the experimental out-of-domain rule detects it, but does not fix the inverted budget. Vietnamese case is a single exploratory observation; no supported-language or robustness conclusion follows.

## Engineering recommendation and acceptance

| Option | Evidence / recommendation |
|---|---|
| A: production prompt + local model | Reject for activation: P0 category 4/24 and 8/24 inversions. No architecture change, but poor reliability. |
| B: compact prompt + local model | P4 has stronger category/completeness and fast warm latency but 9/20 held-out inversions; reject for activation. |
| C: optimized prompt + existing experimental rules | Small shared-slot improvement but no inversion improvement. Additional behavior and regression surface do not justify promotion. |
| D: larger local model + existing contract | Recommended next experiment, not a proven winner; hardware/latency and model availability must be measured. Download only with authorization. |

Keep Phase 8's no-hallucinated-constraint and fail-closed requirements, and Phase 18 route-specific validation, security, failover and approval gates. Do not lower acceptance to fit this model. Require zero observed critical inversion/hallucinated mandatory constraints on an independently reviewed representative set, explicit foreign-currency and exclusion handling, appropriate uncertainty bounds for sample size, no material regression against the frozen baseline under the same scorer, and successful security and integration testing. Zero observed failures in a small sample is not proof of zero risk. Clarify unsupported requests rather than silently dropping mandatory constraints. The observed results fail these gates.

Before integration: independently adjudicate labels, implement a common scorer for stored Phase 8 outputs and new outputs, assemble a fresh held-out set, evaluate larger available local candidates with the same contract and fixed settings, separately test any narrowly scoped deterministic validation on corrections/multiple currencies/ratings/negation/Vietnamese, and rerun security and end-to-end Gateway acceptance only when an eligible native adapter and authorization exist. No extra inference pass, external service, retrieval or embedding changes are justified by the present evidence.
## Existing experiments and remaining evidence gaps

The repository's original 50-case production fixture is `tests/fixtures/query_understanding_cases.json`; the Phase 8.1 development and 20-case historical held-out fixtures are `dev_evaluation_cases.json` and `heldout_evaluation_cases.json`. The separate Phase 8.2 `dev.json`, `validation.json` and `heldout.json` exercise refined v2 behavior, and were not used for this v1 prompt tuning. `src/shopassist/llm/evaluation.py` implements the original slot and preference scoring; Phase 8.1 and Phase 8.2 have separate metric/runner modules, caches, candidates and rule strategies. The historical E1/E5 and Phase 8.2 candidates include compact, contrastive, few-shot, temperature, required-v2 and conservative-rule comparisons; the Phase 8.2 final report makes clear that broad live optimization was deferred, so their presence is not evidence of a new live winner. The existing experiment framework targets Gemini or an eligible Gateway route; the isolated native runner avoids changing either and preserves the Phase 18 ledger.

The sampled adversarial cases do not cover all combinations of role spoofing, credential exfiltration, invented attributes, unrelated output, or multilingual instructions. No direct context-window increase, description-only schema ablation, alternative model size, independent semantic-query grading, fully controlled CPU/GPU comparison, or large cold-start distribution was run. Those hypotheses remain open. The P4 held-out 3/20 exact score is a strict case-folded shared-slot measurement, not a separately adjudicated semantic-equivalence result. The sampled fixture and small counts make model-wide generalizations unsafe; nevertheless the repeated mandatory-constraint failures are enough to reject this particular configuration for activation.
